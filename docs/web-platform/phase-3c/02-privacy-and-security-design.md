# Phase 3C — Privacy and security design

**PROPOSED CHANGES**, unless identified as existing. No safeguard in this document is claimed implemented by Phase 3C.0. Repository facts and symbols are in the [audit](01-current-state-audit.md). The design extends accepted private-by-default Supabase ownership; it does not change Identity.

## Access and publication model

| Caller/resource                | Own active profile API                                        | Other base rows | Public username page/projection                           | Avatar delivery                                        |
| ------------------------------ | ------------------------------------------------------------- | --------------- | --------------------------------------------------------- | ------------------------------------------------------ |
| Anonymous                      | 401                                                           | No grants       | Public only, regardless of discoverable                   | Only current avatar of currently public active profile |
| Verified owner                 | Own whitelist DTO, own revisions                              | No              | Same public rules; private preview belongs to owner route | Own current avatar with session, even when private     |
| Verified other user            | Their own record only                                         | RLS denies      | Same result as anonymous                                  | Same public rules as anonymous                         |
| Deleting/uninitialized account | Deny active writes; explicit recovery/unavailable owner state | No              | Deleting/missing privacy always unavailable               | No public bytes; owner deletion state denied           |

Missing/private/deleting/missing-privacy usernames return the same generic 404 body, noindex and no identifying metadata. A dependency outage returns generic 503 rather than being reported as account absence; do not include submitted handle in diagnostic metadata. Public route must not special-case owner access to private data. A public non-discoverable page is intentionally accessible and guessable; discovery exclusion is not secrecy. External copies/screenshots/search caches of previously public data cannot be revoked.

Keep existing UUID direct reader and public-list semantics. Add exact username projection owned by the existing restricted reader role, fixed empty search_path and fully qualified tables. Join privacy, require visibility public and no deletion marker. Never read base profiles anonymously or elevate a general public page query to service-role access. PUBLIC execute revoked; anon/authenticated explicitly granted. Whitelist output keys and review function-owner column grants. `avatar_path` stays denied to this role.

For metadata, propose a narrowly approved `indexable` boolean in the new page projection, computed only after public authorization from discoverable. It is not a private privacy-row DTO, and is not added to the existing UUID/list return types. No second discovery-list scan to infer indexing. Decide and specify this additive projection in D-05 before implementation. Public DTO mapper strips the page-only signal.

## Validation, transport and concurrency

Proposed form normalization: trim surrounding ASCII spaces and ASCII-lowercase username before existing canonical validation; empty form handle explicitly becomes null, omitted field is unchanged. Display name trims surrounding ASCII spaces; bio preserves content except CRLF→LF. Do not silently transliterate Cyrillic, collapse internal whitespace, accept HTML, or apply Unicode normalization without a contract. Preserve PostgreSQL/code-point limits and reserved handles. Existing SQL still rejects raw uppercase; client/server tests distinguish normalized form input from canonical raw-RPC input. SQL currently treats btrim-empty display name as invalid for publication; broader Unicode-blank rules are not silently promised (D-04).

Proposed HTTP: verified active principal, exact configured Origin for cookie mutations, content-type validation, bounded **actual streamed UTF-8 bytes** before parsing (suggest 16 KiB JSON; header length is not authority), strict Zod envelopes, and no client owner/role/path fields. Read/write using caller JWT. Do not copy auth adapter's text-character size check as a byte-size guarantee. Add request IDs without logging tokens, profile drafts, raw SQL or availability queries.

Use opaque strong If-Match ETags for the corresponding profile or privacy revision. Missing→428, malformed→400, stale SQLSTATE 40001→412 revision_conflict; 23505→409 username_unavailable; 22023/23514→422 validation_failed (safe field codes only); unauthenticated→401; inactive/deleting owner→403; oversized→413; unavailable dependency→503. Do not blindly map all 42501 errors to an account-disclosing public response. Public private/missing remains generic 404. Handle not reserved/occupied distinctions through the same safe username-unavailable feedback; syntactically invalid input may explain format. Proposed accepted rate limiting returns 429 with Retry-After, using trusted shared infrastructure chosen in D-10, not an in-memory distributed-security claim.

Revisions are independent. Existing lock_owner serializes profile/privacy writes on the same profiles row. A successful profile write followed by a read can observe another newer edit: 3C.1 proposes explicit **reload-current** semantics, returning the current owner DTO/ETag and informing the client if it differs from its submitted draft. If an exact committed snapshot is required, implement a new atomic returning RPC instead. Never overwrite by automatic stale retry. Privacy save guards only privacy revision, not the last viewed profile revision; it publishes current valid profile data. Publishing a specific reviewed profile snapshot would need a dual-revision RPC (D-03).

Availability: no new anonymous username-availability endpoint or bulk handle scan. Save conflicts necessarily reveal that a valid name is unavailable, including for private accounts. Apply bounded requests and abuse controls, return no owner identity/reason and make no constant-time/non-enumeration guarantee. Existing direct provider recovery behavior/timing is outside Phase 3C; preserve archived SC-309 generic feedback.

## SSR, routes, metadata and caches

Use dynamic RSC public/owner pages and request-scoped no-store provider reads. Explicitly apply `Cache-Control: private, no-store, max-age=0, must-revalidate` to profile HTTP/image/error responses; protect HTML/metadata responses for anonymous requests too, since existing refreshSession only sets these headers for session-bearing requests. Implementation must verify CDN/header behavior and Next route output rather than assuming dynamic rendering alone supplies every header.

No persistent React/Next data cache, ISR, static username generation or shared profile cache. Request-local deduplication of the **safe public projection** may keep page and metadata consistent within one request; it must not cross users/requests. If privacy changes between an authorization snapshot and transmission, a response already in flight cannot be recalled. Revocation means requests authorized after the committed change deny access; do not promise to erase an already downloaded page/image.

After successful mutations, return fresh revisions and refresh relevant owner/current public routes. Clear obsolete local owner draft/preview state on logout; cancel pending requests and ignore superseded results. Browser history/router snapshots may retain bytes already received: refresh/back-navigation tests and no persistent app cache limit this; they cannot provide remote erasure. Avoid an optimistic public-preview path that renders owner data before permission is confirmed.

Canonical proposal: locale-specific absolute configured site origin + `/en/u/<current-handle>` or `/ru/u/<current-handle>`; reciprocal language alternates use the same current handle. UUID stays identity/FK; Phase 0 UUID canonical path was a proposal, not an accepted immutable routing rule. Renamed handles have no redirect history by default. Mixed-case valid ASCII public URLs may redirect to lowercase **only after a successful authorized lookup**; missing/private variants produce the same unavailable result. Unknown locales are 404.

Metadata: discoverable public page may be index/follow; public non-discoverable is noindex/nofollow and absent from platform discovery/sitemaps. Private/missing/deleting use generic localized unavailable title, no bio/avatar/identifying canonical/OG fields, noindex via metadata and response X-Robots-Tag. Default all public pages to noindex if the approved indexing signal is unavailable; never infer discovery from direct visibility alone. Use sanitized plain presentation text, with description length bounded; no raw user HTML or unsafe JSON-LD. Resolve unavailable result before streaming identifying content; test actual HTTP status because framework streaming can affect not-found status. No sitemap/catalog UI is required; future consumers must use the filtered list contract.

## Avatar storage and capability design

Existing facts: Storage is disabled, avatar_path reserved, avatarUrl null-only, no setter/cleanup capability. These migrations and capabilities are future design, not configuration made here.

Recommend a **private** bucket, immutable random paths `owner-uuid/random-object-id.webp`, no overwrite/upsert, no public bucket or reusable signed download URL. Public/owner DTOs expose only opaque application URLs `/api/v1/profile-avatars/<avatar-id>`, never storage paths or URLs. Bypass Next image optimization and CDN caches for these privacy-dependent bytes; a plain bounded image can preserve the endpoint's no-store policy. Default decorative avatar alt is empty beside a visible profile name; provide localized meaningful alt only where the image adds identification.

Start with server-mediated upload using the existing Next + Supabase stack. Provisional budgets for approval: ≤2 MiB request image, JPEG/PNG/WebP only, ≤4096 per axis and ≤16 megapixels decoded, output ≤512×512 WebP and ≤1 MiB; reject animation/SVG and malformed/decompression-bomb content. Check byte signature and decoded format/dimensions, bound resource use, strip EXIF/location metadata by re-encoding. Browser accept/MIME/extension checks are advisory only. Confirm the installed server decoder's supported runtime and direct dependency declaration before use; no dependency is installed by planning. Multipart overhead needs a separate strict request ceiling and streaming parser design; never read an unbounded body before the limit.

Proposed server capability: a confined server-only storage adapter may use a server credential for Storage upload/download/delete and a **service-only avatar-resolution RPC**, never for ordinary profile reads/writes. That RPC returns the current locator only after checking target avatar-id, current reference, deletion state and visibility; owner delivery additionally requires a separately verified principal. Never trust a supplied owner UUID without that verification. Recheck authorization immediately before starting a bounded stream, and fail closed on lookup errors. No anonymous/authenticated EXECUTE on this locator RPC; default PUBLIC execute revoked. A more restricted runtime role is preferable if deployment supports it, but the existing SDK with a tightly isolated server-only secret is the baseline proposal. This capability is broader than caller-JWT RPC access and requires explicit D-08 approval/security review. Do not put it in public env, client barrel graphs, browser SDK or logs. Do not use a privileged general lookup to implement username pages.

Storage policy matrix: private bucket; anon and authenticated raw object SELECT denied; raw INSERT/UPDATE/DELETE denied in the server-mediated design. This is stricter than owner-path write policies and prevents deletion/overwriting of the current avatar outside revision/cleanup orchestration. Server adapter constructs owner path from verified principal; caller cannot choose bucket/path. A privileged storage key bypasses RLS, so policies alone do not secure that adapter: its authorization and limited interface need independent review and negative tests. If direct owner uploads are later preferred, they require a staging-only prefix, no current-object delete/update grants and a separate approved policy/validation contract, not an implicit extension.

### Upload/replace/remove transaction and cleanup

1. Verify active owner, origin, byte/resource budgets and expected profile revision; create a durable pending upload record **before** object creation. Store generated owner/path/id, state and timestamps internally. Enforce a bounded number of pending objects and age/quota limits atomically.
2. Decode/re-encode and write a new immutable object using only the generated path. Failed upload leaves a retryable pending record; never replace the current pointer first.
3. A caller-JWT controlled commit RPC locks the profile, checks active owner, expected revision and pending-record ownership/readiness, associates only the generated upload, increments profile revision and transactionally schedules previous-object cleanup. An arbitrary avatar_path setter is forbidden. The trusted processing step marks readiness through a service-only capability, not caller claims.
4. If commit conflicts/fails, retain current avatar and schedule cleanup of only the new unattached object. A crash after upload but before commit is reconciled from the pending ledger. Use an operation id for retry: record already committed result and never let a retry remove a current object.
5. Remove RPC clears the current pointer and queues its old object in the same DB transaction; physical Storage deletion follows. Fresh requests for old avatar-id fail immediately, even if bytes remain in the bucket. Removal retry is idempotent with explicit revision/operation semantics.
6. A durable runner retries cleanup with bounded attempts/backoff/observability and checks the object is not current before deletion. Reconciliation handles pending uploads, failed deletes and lost responses; never delete by arbitrary browser path. Do not cascade away cleanup records with auth.users: retain minimal opaque locator/work state long enough for retry. Account-deletion orchestration remains out of scope; document an operational orphan-cleanup hook when Auth rows disappear.

Storage and PostgreSQL cannot commit one transaction. A queue plus an actual durable runner/scheduler and retention policy are required; a best-effort in-request finally block is insufficient. D-09/D-10 block 3C.3 until capability, schema, retention and scheduling ownership are accepted. No new worker/backend is assumed; a protected existing deployment scheduler invoking a narrow Next cleanup job is the preferred integration if available. Its identity and authorization must be specified before implementation; no unauthenticated cleanup endpoint.

## Threats, controls and test obligations

| Threat                                                  | Verifiable control                                                                         | Planned scenarios / layer                               |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------- |
| Private direct URL / anonymous or authenticated probing | Same public authorization/404 and key whitelist; owner route separate                      | SC-408/410/415; real SQL/REST + SSR browser             |
| Cross-user read/mutation, forged owner or metadata      | JWT-derived ownership, SELECT RLS + revoked DML, strict envelopes                          | SC-401/411; real PostgreSQL and direct Data API         |
| Handle enumeration / case duplicates                    | No availability endpoint; normalized save + unique index, generic conflict, bounded abuse  | SC-402/403/412; unit + real concurrent REST             |
| Rename stale links and reuse impersonation              | Current-handle lookup; explicit old-handle policy/confirmation, no identity reassignment   | SC-409; browser + SQL; D-06                             |
| Discovery leakage                                       | public AND discoverable list; noindex non-discoverable; direct links intentionally allowed | SC-407/408/415; SQL + metadata                          |
| Metadata/RSC/email/path leak                            | One whitelisted public reader, generic unavailable metadata, raw-response inspection       | SC-410/415; SSR integration/browser                     |
| Shared private cache / stale publication                | No-store HTML/JSON/bytes/errors, no shared data/image cache; privacy rechecked             | SC-407/410/414; HTTP + browser                          |
| Object guessing or signed URL exposure                  | Private bucket, denied direct roles, opaque application URL and current-pointer check      | SC-413/414; real Storage + bundle/response inspection   |
| MIME spoof, huge decode or metadata exposure            | Actual bytes/decoded dimensions/re-encode/budgets; no SVG/animation                        | SC-413; unit processing + real upload integration       |
| Untrusted profile HTML/URLs                             | Plain text React output, strict schema, no raw sinks/user-supplied avatarUrl               | SC-404/415; unit + SSR/RTL                              |
| Concurrent edits/replace/remove                         | Row lock + independent expected revisions; no stale retry; immutable upload/CAS            | SC-405/406/412/414; real simultaneous REST/Storage      |
| Bootstrap missing/partial and deletion                  | Existing atomic ensure_profile; missing privacy denies; inactive owner checks              | SC-416; real SQL/Auth + browser                         |
| Orphans/crashes/delete failure                          | Pre-upload durable record, transactional cleanup enqueue, idempotent worker/reconciliation | SC-414/417; restart/fault-injection Storage integration |

The scenario identifiers are planning-local IDs, not recorded workflow evidence. Residual risks: unavoidable copies of published content, in-flight authorized responses, handle unavailability inference, privileged runtime compromise and unresolved deployment abuse/cleanup infrastructure. Resolve release-blocking risks before the affected stage; do not present noindex or React hiding as access control.
