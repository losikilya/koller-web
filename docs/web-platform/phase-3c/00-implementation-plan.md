# Phase 3C — Implementation plan (planning only)

Date: 2026-10-26. Phase 3C.0 produces documentation only. **Implementation is not authorized.** Facts and evidence: [audit](01-current-state-audit.md); safeguards: [security design](02-privacy-and-security-design.md); future tests: [acceptance](03-acceptance-scenarios.md); decision gates: [open decisions](04-open-decisions.md).

## Scope and workflow

Plan own-profile viewing/editing (username, display name, bio), private/public and discovery settings, EN/RU SSR `/u/:username` pages and safe avatar selection/upload/replacement/removal. Preserve UUID identity, existing Supabase Auth/SSR/RPC/RLS, private defaults and reserved showActivity=false.

Non-goals throughout: reimplementing registration/auth, new OAuth providers, follows, feed/activity/history, events/battles, timer/presets/rankings, mobile synchronization, full account-deletion orchestration, payments, new state manager/backend/microfrontend infrastructure. Do not add placeholders for them.

Recommend **one future** `phase-three-c-profiles-privacy` OpenSpec change, with sequential 3C.1–3C.4 task groups and shared contracts. There is no implementation change or canonical feature scaffold in 3C.0. A planning report is not a scoped-maintenance cleanup, executable BDD or TDD evidence. Before implementation approval: resolve blocking decisions, use `pnpm spec new change ... --schema frontend-bdd-tdd`, obtain CLI status/instructions for proposal → specs → design → bdd → test-plan → tasks. Update stable specs only through later authorized native archive; preserve current archives byte-for-byte. If genuinely independent later release scope emerges, split prospectively rather than opening parallel changes now.

Before the first implementation, record original full GREEN and relevant real SQL baseline; run workflow check. New behavior needs actual assertion RED, unchanged-test GREEN then REFACTOR. Existing SQL/auth guards may be explicit preimplementation baseline scenarios with reasons; never call a setup failure RED or backfill evidence. Keep one test process at a time. Completed implementation requires full pnpm verify, actual independent review, workflow ready and separate product acceptance; no archive/commit/push/deployment is authorized by this plan.

## 3C.1 — Profile Management

- Preconditions: owner separately approves implementation, blocking D-01/D-02/D-03/D-06 closed; future OpenSpec artifacts/workflow check and baseline complete; architect confirms boundary plan.
- Scope: authenticated My Profile and edit form, nullable handle/private draft, display name/bio, normalization, field validation, username conflict and stale-revision handling; safe owner read and profile PATCH.
- Non-goals: public pages/privacy publication changes, uploads and preferences editor; all global non-goals above.
- Affected paths: proposed account/profile route, modules/profile service/repository/editor/policy, contracts, app HTTP adapter, EN/RU profile namespace, `/account` navigation, mirrored tests.
- Migrations/contracts: **no new SQL required for basic editing under the current immediate-reuse policy**. If D-06 instead selects handle reservation, an atomic reservation migration is required in 3C.1 before rename can ship. Reuse update_own_profile and existing constraints. Add revisioned owner schemas, lossless ETags and typed error mapping. Preserve raw-RPC uppercase rejection; normalize form handles at server ingress before canonical patch validation.

Existing ownership/SQL behavior gets baseline classification; new HTTP/UI behavior gets RED.
- Acceptance: only verified active owner reads/saves; successful UI reflects fresh result; duplicate handle returns generic unavailable; stale update never overwrites; invalid fields retain draft and focus errors; bootstrap retry preserves session. No private data in cache/logs.
- Risks/dependencies: bigint precision, request races, null handle semantics, sensitive payload rendering; depend on Phase 3A/3B, existing UI and root workflow.
- Independent review: read-only reviewer checks contract and engineering after real checks; architect consulted before any public boundary change. Only orchestrator writes.

## 3C.3 — Avatar Management

- Preconditions: privacy/public contract GREEN; D-07 through D-10 approved; local Storage enabled in a separately reviewed implementation configuration change, without database reset; real Storage test harness ready; acceptable decoder/budgets confirmed against installed dependencies.
- Scope: native accessible selection/preview, bounded server-validated image processing, upload association, replacement/removal, immediate logical revocation and durable retryable physical cleanup. [Security design](02-privacy-and-security-design.md) defines the proposed transaction/saga boundaries.
- Non-goals: cropping studio, arbitrary media/SVG/GIF, public bucket/signed public URLs, full account deletion worker or CDN optimization.
- Affected paths: AvatarEditor/service/server storage adapter, `/me/avatar`, controlled image route, contracts avatarUrl schema, profile association RPCs, future Storage/ledger migrations and policies, supabase/config.toml, local acceptance tooling and tests; generated DB types.
- Migrations/contracts: existing avatar_path is a reserved locator only and no setter exists. Need private bucket limits/policies; controlled owner-derived revisioned association RPC; upload/cleanup ledger with old-object cleanup scheduled transactionally. Keep raw avatar path inaccessible to public projection role. DTO exposes opaque application URL only. No arbitrary path in profile PATCH.
- Tests: real Storage REST using anonymous/owner/other credentials, spoofed MIME/decode/byte/pixel limits, overwrite/path traversal, concurrent replace/remove, attach failure compensation, cleanup retries/crash windows, current privacy checked on every image request, local keyboard/reflow/a11y browser journeys.
- Acceptance: current avatar remains on failed replacement; remove clears reference before cleanup; stale uploads cannot win or delete current object; private/deleted/old URLs reveal no bytes; no privileged credential/path in browser/metadata/logs. Cleanup survives process restart.
- Risks/dependencies: privileged storage capability, image decoding resource abuse, cross-system non-atomicity and durable scheduling; release blocked until genuine Storage acceptance and runtime dependency review pass.
- Independent review: architect signs capability/storage boundary; reviewer inspects authorization/negative Storage tests and failure recovery; orchestration remains single writer.

## UX and localization contract

My Profile shows current owner fields, privacy badge, Edit/Privacy actions and safe public-link action only when meaningful. Edit uses Input for username/name, native labelled textarea for bio, inline errors plus focusable error summary, explicit Save/Cancel and pending disabled submission. Keep drafts on validation/network/conflict failure; explain conflict and offer reload, never silently retry stale patches. Privacy uses labelled native radio choices and checkbox, explain that public direct links still work when discovery is off; hiding resets discovery and does not auto-reenable it on later publish. Avatar uses labelled native file input, keyboard-accessible Replace/Remove, textual constraints, announced progress and revocable local preview URL cleanup. Cancel cannot undo an already committed server mutation.

Use Container/Card/Button/Badge/LoadingIndicator/EmptyState/Dialog only as their existing contracts allow. Native controls may be styled in Profile SCSS using shared tokens; a new shared primitive requires demonstrated reuse. Errors/loading/success have localized announced text; unavailable profile has generic localized title with no identifying metadata. Distinguish loading, empty, absent, service failure, bootstrap retry and forbidden owner states. All product text and metadata use EN/RU profile messages with parity checks; API codes stay locale-neutral. Preserve 320px reflow, reduced motion, visible focus, labels and logical heading order. No raw SQL/provider messages reach users.
